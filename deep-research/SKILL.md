# Deep Research

用这个 skill 把 Codex 变成“普通模型可执行的深度研究代理”。它不依赖 deep-research 专用模型，而是靠严格流程、工具检索、证据表和充分性判断来逼近 ChatGPT Deep Research 的体验。

## 核心原则

- 先收集证据，再写结论。不要边搜索边直接产出最终观点。
- 区分事实、推断和建议。事实需要来源，推断需要说明依据，建议需要说明适用条件。
- 对最新信息、价格、政策、法律、模型、公司、人物、产品能力、库版本、标准和新闻，必须检索确认。
- 优先使用一手或权威来源：官方文档、标准、论文、财报、监管文件、项目仓库、权威数据库。
- 对技术库、SDK、框架、云服务和 API 问题，优先使用可用的官方文档工具或 Context7；没有时再检索官网文档。
- 发现冲突证据时不要抹平差异，要列出冲突来源、可能原因和当前更可信判断。
- 如果证据不足，明确说“不足”，并说明缺口，而不是强行给确定结论。

## 工作流程

### 1. 澄清研究任务

先判断用户问题是否足够清楚。若以下信息会显著影响结果，最多问 3 个澄清问题：

- 研究目标：要做决策、写报告、做方案、做对比，还是找资料？
- 范围边界：地区、行业、时间段、对象、竞品、技术栈。
- 输出形式：简报、长报告、表格、决策建议、PPT 大纲、代码方案。
- 来源偏好：是否只要官方资料、是否可用中文资料、是否包含本地文件或知识库。

如果用户要求直接开始，或合理默认不会带来高风险，就先列出默认假设并继续。

### 2. 建立研究简报

在心里或工作笔记中形成一个简短 research brief：

- `objective`: 用户最终要回答的问题。
- `scope`: 时间、地域、对象和排除项。
- `deliverable`: 最终输出格式。
- `decision_context`: 用户可能如何使用这个结论。
- `risk_level`: 是否涉及医疗、法律、金融、安全、合规等高风险领域。
- `freshness_need`: 是否需要当前资料。

### 3. 拆解子问题

把主问题拆成 4-10 个可检索的子问题。好的子问题应该覆盖：

- 定义和背景。
- 关键事实和时间线。
- 主要参与方、方案或竞品。
- 对比维度。
- 成本、风险、约束和不确定性。
- 用户关心的决策标准。

每个子问题都要能被证据支持或反驳。

### 4. 制定检索计划

为每个子问题生成 2-5 条查询或检索动作。按来源类型选择工具：

- `web`: 当前事实、新闻、价格、官方页面、公开资料。
- `browser`: 需要打开页面、检查动态内容、截图、交互验证。
- `rg` / 本地文件读取：用户给出本地仓库、文档、日志、报告路径时。
- GitHub / GitLab：仓库、issue、PR、release、项目活跃度。
- 文档、表格、PPT 技能：用户提供 `.docx`、`.pdf`、`.xlsx`、`.pptx` 时。
- 知识库或向量检索：用户要求基于内部资料或已有知识库。

检索时先广后窄：先确认权威来源和基本事实，再追查细节、冲突点和反例。

### 5. 建立证据表

不要把搜索结果直接揉进报告。先整理成证据项。需要详细结构时读取 `references/evidence-schema.md`。

每条证据至少包含：

- `claim`: 该证据支持的主张。
- `source`: URL、文件路径、仓库、论文或数据来源。
- `source_type`: 官方文档、论文、新闻、博客、代码、监管文件、本地文件等。
- `summary`: 用自己的话概括证据。
- `reliability`: high / medium / low。
- `supports`: 支持哪个子问题。
- `limitations`: 证据局限、时间范围或偏见。

引用文字要短，优先转述；不要复制长篇原文。

### 6. 判断证据是否充分

在写报告前做 sufficiency audit：

- 每个关键子问题是否至少有 1 个高可信来源，或 2 个中等可信来源？
- 是否存在只来自单一来源的关键结论？
- 是否有冲突资料没有解释？
- 是否缺少当前性验证？
- 是否存在用户会据此投入大量时间、金钱或承担风险的建议？
- 是否把观点当成事实了？

如果不充分，进行第二轮检索。通常最多迭代 2-4 轮；如果仍不足，报告中明确列出证据缺口。

### 7. 综合与写作

最终报告要从用户的决策需求出发，而不是堆资料。需要完整模板时读取 `references/report-template.md`。

默认结构：

```markdown
# 标题

## 摘要
用 5-8 条说明最重要结论、建议和不确定性。

## 研究范围与方法
说明范围、时间、检索方式和重要假设。

## 关键发现
按主题组织，每个关键事实都带来源。

## 对比 / 分析
用表格或分节比较方案、竞品、观点或证据。

## 建议
给出可执行建议，并说明适用前提。

## 不确定性与证据缺口
列出仍无法确认的内容。

## 来源
列出使用过的主要来源。
```

### 8. 最终自检

发送结果前检查：

- 是否回答了用户的原始问题？
- 关键结论是否有来源？
- 是否标注了日期、版本、地区等条件？
- 是否明确区分事实和建议？
- 是否避免了未经证实的绝对化表达？
- 是否没有把检索过程的噪音塞进最终报告？

## Codex 执行规范

- 研究过程中要定期告诉用户正在查什么、发现了什么趋势。
- 使用本地文件时优先 `rg` 和有针对性的读取。
- 对会变化的信息必须使用互联网或当前文档工具确认。
- 对 OpenAI、SDK、框架、云服务等技术文档，优先官方文档或 Context7。
- 如果用户只要“快速结论”，可以缩短检索轮次，但仍要标注证据不足处。
- 如果用户要求“完整深度研究”，要完整执行拆解、检索、证据表、充分性判断和报告。

## 可选输出：证据表

用户要求透明过程、审计、可复查研究时，在最终报告前或附录中输出证据表。否则只在内部使用证据表，并在报告中列出关键来源。

## 触发示例

- “帮我深度研究一下 Codex 怎么复刻 ChatGPT Deep Research。”
- “做一份 Cursor、Codex、Claude Code 的竞品分析。”
- “调研一下这个技术方案是否适合我们团队。”
- “基于这些本地文档，给我一份带引用的行业报告。”
- “不要用 deep-research 模型，用普通 Codex 帮我做深度研究。”
